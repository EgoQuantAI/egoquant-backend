# EgoQuant security and compliance

Status: 20 October 2026, the version tagged `submission-20oct`. Items marked **PENDING** are not finished; nothing below claims more
than the code does. Every claim names the file or test that backs it.

## 1. Permission tiers

| Tier | What it may do | What it may never do |
|---|---|---|
| Visitor (no account) | Questionnaire, Risk Game, a portfolio report, the advisor chat. IBKR data may be sent with one request and is used once. | Store anything on the server. |
| Signed-in user | Everything above, plus: connect IBKR data to the account, save reports, check planned trades, record a trade they made, read their activity log, delete their data or account. | See or change another user's data (Row-Level Security + backend filter). |
| EgoQuant (the system) | **Read-only** access to the investor's IBKR trade history; **advice only**. | Place, change or cancel orders; move money; ask for or accept an IBKR username or password. |
| The LLM (advisor chat, Agent D) | Explain engine facts in plain words; label a headline's tone for one fund (Agent D, see 6); call TWO read-only tools, `run_what_if` and `check_trade` (signed-in investors only), whose arguments are validated and whose numbers come from the deterministic engine. | Set any score, C-level, weight, limit, approval or trade verdict; supply an identity; change any data or limit; quote a number the engine did not produce (blocked, see T15). |

## 3. Privacy

- **Consent:** a versioned consent (`consents`, `CONSENT_VERSION`) is required before IBKR data is connected; a changed text needs new consent.
- **Data minimisation:** per trade only date, symbol, side, quantity, price, currency, asset category and net cash. No account number, name or description. Chats are not stored. Uploaded files and tokens are never stored.
- **Retention:** every row expires after 180 days (`expires_at`); `purge_expired()` runs daily via pg_cron when enabled (otherwise by hand: **Savas, enable pg_cron**).
- **Delete:** `DELETE /account/data` erases every stored row; `DELETE /account` deletes the account and cascades.
- **Onboarding answers** (`supabase/migrations/005_onboarding.sql`, `GET`/`PUT /account/onboarding`): onboarding needs an account; the questionnaire answers, profile, preferences, goal inputs, Risk Game result and a pointer to the saved report are kept in one `onboarding` row per user (RLS, 180-day expiry, erased by `delete_my_data()`, shape and size checked, `extra="forbid"`). Display state only: `/portfolio` re-scores the answers every time. The browser drops another user's copy at sign-in and its own at logout.
- **What-if audit and privacy counts** (`supabase/migrations/002_what_if.sql`): signed-in users' what-if runs are kept in `what_if_runs` (scenario, result summary, seed, path count, engine version, status, a 16-character fingerprint of the base context; no answers, weights or text) and the per-session redaction COUNTS in `privacy_log`; both have RLS, 180-day expiry, and are erased by `delete_my_data()`. `GET /privacy-log/{session_id}` returns only the user's own counts. Anonymous chats store nothing (an audit log line with counts only).
- **Questionnaire answers with a saved report:** since 19 Oct a report saved from `/account/portfolio` keeps the answers it was built from (`reports.report -> inputs.answers`: the chosen options, the amount invested and the amount needed; never the questionnaire score) because the on-chain seal fingerprints them. It is the owner's own row (RLS), expires after 180 days and is erased by `delete my data`. Visitors' answers are still never stored.
- **Profile picture** (`supabase/migrations/003_avatar.sql`, `PUT /account/avatar`): one of five built-in pictures, or the user's own small JPEG/PNG/WebP (resized to 160 px in the browser, at most 64 kB, magic bytes checked on the server, a database CHECK as a second lock). SVG is never accepted because it can carry script. It is personal data the user chose to add: it lives in `profiles.avatar`, is shown only to its owner, and is deleted with the account. The server does not strip image metadata; the browser's resize re-encodes the picture.
- **Logs:** the operation log records user-confirmed actions (consent, data connected, report generated, warning shown, trade checked/recorded) with counts, dates and labels only. Server logs carry exception types and routes, never request bodies.

## 4. Known risks and gaps (honest list)

1. The RLS proof `supabase/tests/rls_isolation.sql` **passed on the real Supabase project on 19 Oct** (`docs/supabase/SUPABASE_LOG.md`), and the Data API refuses anonymous reads on every table. Still being re-verified on 20 Oct (Bideci's AI): which of migrations 004 to 007 are applied, the two-user live smoke test `supabase/tests/live_smoke.py` against the deployed backend, and the retention job. Nobody has click-tested the whole account flow end to end on the live site yet. **PENDING (re-verification).**
2. Trade check: logic (D1), endpoints (O4), chat explanation (B2) and UI (U7) are built and unit-tested. A visitor can also check a trade (`POST /trade-check`, holdings from the IBKR report or token in that one request, nothing stored, no "I made this trade"). Still **PENDING**: the live model red-team, the property sweep, and a click-through in the browser.
   "I made this trade" records the trade as the **user reports it** (price and quantity they enter); EgoQuant never places an order and cannot verify the trade until the next IBKR import. A recorded trade is kept as source `user_recorded` and survives a re-import.
3. Supabase's built-in email sender has a low hourly limit: custom SMTP or pre-created demo accounts are needed for a live demo.
4. The confirmation email link must be changed in Supabase's template to `{{ .SiteURL }}/api/auth/confirm?token_hash={{ .TokenHash }}&type=signup`.
5. Binance read-only API keys: **roadmap**, not built. Design: verify the key's permissions via `GET /sapi/v1/account/apiRestrictions` and refuse any key that can trade, withdraw or transfer; fetch once; never store.
6. `/debug/portfolio` answers 404 unless `EGOQUANT_DEBUG_PAGES=on` (unset in production); when on, it is public (synthetic data only, own rate limit).
7. The old Tiingo key in the private git history was rotated on 20 Oct (about 16:25) and the public repositories are one-commit copies without that history.
8. Railway needs a volume at `EGOQUANT_CACHE_DIR` so price caches survive redeploys (availability, not security).
9. What-if: `supabase/migrations/002_what_if.sql` must be run in Supabase (Savas) before signed-in runs are audited;
   until then the audit insert fails quietly (logged) and the chat still works.
10. What-if limits: the rate limit is in memory (per process, reset on redeploy); a timed-out run keeps its worker
    thread until it finishes (two threads, so at most two heavy runs at once); `reoptimize` is refused for portfolios
    built from an uploaded IBKR report or a Flex token (the raw history is never kept), and works from saved account
    history only when signed in.
11. Because every reply is number-grounded as a whole, `/chat/stream` sends the reply once it is checked (the same
    events as before, no word-by-word typing).
12. **Request-body size limit is by declared length only.** `main.py` (`BodySizeLimit`, `tests/test_body_limit.py`) refuses a body whose Content-Length is over 4.5 MB (`/portfolio`, `/trade-check`, `/account`, `/debug/portfolio`), 512 KB (`/chat`, `/briefing`, `/what-if`) or 1 MB (anything else) with a 413 before it is read, and a body of unknown length (chunked) with a 411. A client that lies about its length is not stopped by this check; Railway's own proxy limits apply in front of it.
13. `username_available` can be called straight through Supabase's REST API with the public key, which bypasses the backend's 60/min limit: usernames can be enumerated (yes or no only). Accepted by design.
14. `operation_log` is insert-only for the user, but a user can add entries for themselves directly, so it is an activity record, not a tamper-proof audit log.
15. Supabase's free plan cannot edit the confirmation email template without custom SMTP. With the default link the email is confirmed but the user lands on the homepage signed out and logs in by hand (gap 4 describes the intended link).
16. The `what_if_context` seal is a signature, not encryption: it carries the user's own questionnaire answers back to their own browser. It is never put in a prompt.
17. Agent B: when real-history evidence is not stricter than the class limit it now sends no loss limit at all (it never loosens a limit, it just adds none).
18. **The old Tiingo key was in the private development history** (commits 33e7eac to 4770747 in the backend). It was rotated on 20 Oct (about 16:25) and the public repositories are one-commit copies without that history.
19. The frontend CSP allows `'unsafe-inline'` and `'unsafe-eval'` for scripts (Next.js needs the first; the second is only needed in development and should be dropped for production). The backend sends `Strict-Transport-Security` since 20 Oct; the frontend relies on Vercel's own HSTS on its domains. Hardening of both (drop `unsafe-eval` in production, `form-action`, `base-uri`, `object-src`, Origin checks on every proxy POST) is in progress.
20. **Closed (20 Oct):** every `POST` proxy route now runs the same-origin check (`sameOrigin()` in `src/lib/server-auth.ts`), including `/api/chat*`, `/api/portfolio`, `/api/trade-check` and the two briefing routes (frontend `3d720c7`); only `/api/debugmodels` has none, and it is a 404 in production. `SameSite=Lax` cookies remain the second line.
21. A 422 no longer repeats a field NAME the client invented (`extra_forbidden`); field names that exist in our schema are still shown, by design.
22. **On-chain sealing is built** (Aslan; `docs/ANCHORING.md`, `docs/ON_CHAIN_EVIDENCE.md`, `docs/JUDGE_GUIDE.md`): a salted 32-byte fingerprint of a confirmed plan goes to the Sepolia TEST chain after an explicit `record_seal` consent. Since 20 Oct (seal v2, `docs/ONCHAIN_DECISIONS.md` OC-09 to OC-14) the fingerprint also covers the exact report that was shown (rendered once into a sealed document, "Sealed for: <username>"), so an edited report next to a genuine seal, or someone else's genuine report, is visible on **Verify a report**; the record carries the person's chosen username (never an e-mail or a user id) inside the salted fingerprint only, and the sealed document is stored in the same owner-only row (`008_seal_v2.sql`). A chain entry cannot be deleted, so delete-my-data removes the record, the salt and the document but not the fingerprint, which reveals nothing without them. Not built: an automatic "this report belongs to my account" check on the Verify page (OC-15); a printed or PDF copy cannot prove itself. Test network only; a real deployment would use a consortium chain.
23. `DELETE /account/data` erases the data tables and clears the profile picture (`007_erase_everything.sql` nulls `profiles.avatar`), but keeps the account and the profile row with the username, so the person can still sign in; `DELETE /account` removes everything (the tables cascade from the auth user).
24. **Migration order.** `supabase/migrations/007_erase_everything.sql` must be the last file run in the Supabase SQL editor, and run again after any future migration that redefines `delete_my_data()` or `purge_expired()`; `docs/supabase/FROM_ONUR_runbook.md` lists the order. Until it is run, "erase my data" covers only the tables of the last of 005/006 that was run.
25. **The Risk Game can raise the attitude to risk** (by at most one third of the distance to its level, never past the capacity cap): a deliberate product decision (Savas, 20 Oct) so that behaviour counts for everyone. A stricter reading (a hypothetical game may only lower) is one switch away: `EGOQUANT_RISK_GAME_MAY_RAISE=off`.
26. **Many simultaneous heavy builds raise memory** (each extra simultaneous build adds about 150 MB and a heavy build alone peaks at 300 to 415 MB for a 10-year goal on the development PC; 20 at once reached about 3 GB there; the Railway service has 1 GB). The build gate is merged and live: one portfolio is built at a time per server process (`EGOQUANT_MAX_CONCURRENT_BUILDS`, default 1); the others wait their turn. Through the website the wait ends after 115 s with the website's own "too slow" answer (`build-timing.ts` `BUILD_PROXY_TIMEOUT_MS` = 115 000); a direct API call gets, after 120 s, a 503 "The service is busy building other portfolios" with Retry-After 30. Worst local test: 20 of the heaviest 60-year builds in the same second: 8 to 11 served, the rest turned away; ordinary builds (5 to 7 s on saved prices) were not flood-tested; no gated run crashed. Rate limits per route stay in place.
27. **The advisor prompt `advisor-v11`** (trade questions through `check_trade`, first-name greeting through a token, report-tab awareness, verdict worded as "within / outside your limits", one size field for the trade tool) **went through the live red-team on 20 Oct**: v10 scored 34 of 42 (all 24 non-trade cases; 8 trade cases failed safely because the model filled both size fields of the trade tool and the server refused the call), the tool now takes one size (v11) and the re-run passed 41 of 42 (the miss is a false positive of the keyword check on a correct reply); trade-explain-v4 51 of 51 (`eval/results/*_20261020_*.jsonl`; `eval/chat_redteam.py`, `tests/test_chat_redteam_trade.py` runs the harness against a scripted model); earlier prompts passed the live runs kept in `eval/results/` (advisor chat, prompts v2 to v5: 19/19, 19/19, 21/21 and 24/24; trade explanation: 22/24 then 24/24, 24/24 and 51/51 twice); the other live checks run on 19 Oct (a regime-wording check) were not kept.
28. **The compliance guard is pattern-based** (`egoquant/advisor/config.yaml`, English and Chinese, 36 patterns after the 20 Oct review): advice-like wording in another phrasing or language can pass it. The prompt (no advice vocabulary, `verdict_words`), number grounding and the deterministic tools are the first lines of defence; the guard is the last.
